1. Likely trigger found and removed
   Our own wallpaper daemon (~/Documents/desktops/workspace-wallpapers-fast.sh) writes the wallpaper to dconf on
   every workspace switch. Both freezes since its Sep 24 fix came right after a burst of those writes
   (Oct 11 13:03:26, today 17:04:10). The likely mechanism, read in the installed source but not yet confirmed
   by a backtrace, is a lock-order deadlock. "dconf worker" holds GLib's GSettings backend mutex and spins on
   GJS's toggle-queue spin lock. The main thread holds that spin lock during GC and blocks on the mutex. That
   matches what you saw.
   With the user's OK, I stopped the daemon at 19:26 and set its autostart entry to false. The backup is
   ~/.config/autostart/workspace-wallpapers.desktop.bak_20261030_192623.

2. Restart a hung shell with SIGINT, not SIGKILL
   - gnome-shell does not catch or ignore SIGINT. The running shell's /proc status shows these caught:
     ILL TRAP ABRT BUS FPE SEGV TERM 33; and these ignored: PIPE XFSZ. So the kernel ends the process on SIGINT
     just as it does on SIGKILL, even with the main thread deadlocked.
   - systemd.service(5), SuccessExitStatus=: "except for Type=oneshot, the signals SIGHUP, SIGINT, SIGTERM, and
     SIGPIPE" count as a clean exit. The shell's unit is Type=notify. So OnFailure= does not fire, and the
     "Oh no" screen does not come up.
   - Test: throwaway units with the shell's Restart=always, RestartSec=0, SuccessExitStatus=1 and an
     OnFailure=. SIGINT and SIGHUP restarted them with no failure logged. SIGKILL logged
     "Failed with result 'signal'" and "Triggering OnFailure= dependencies", which is what happened at 17:25:30.
   - Not yet tried on the real shell.

3. A new command for your runbook: unfreeze-shell
   ~/.local/bin/unfreeze-shell links to CompositorUnfreeze/unfreeze-shell_20261030_192908.sh.
   From the Mac:  ssh -t drn2@<laptop hostname>.local .local/bin/unfreeze-shell
   What it does:
   - It runs your Properties.Get ShellVersion check (two tries, 5 s each). If the shell answers, it stops.
   - It saves thread states and journals to ~/gnome-shell-hangs/<time>/, and offers "sudo gcore"
     (Ctrl+C skips it).
   - It sends kill -INT and waits for the new shell to answer.
   - If the "Oh no" windows appear anyway, it hides them with your xdotool method.
   "--check" is read-only, like your triage script.

   The script can switch the laptop's screen back to the desktop only when it runs on a text console. If the
   user is sitting at a text console while you run it over SSH, ask them to press Ctrl+Alt+F2.

4. Your OnFailure= drop-in lines do nothing, by design

   OnFailure=gnome-session-shutdown.target ends the session. I've told the user to log out and back in when

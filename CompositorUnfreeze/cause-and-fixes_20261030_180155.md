## If it freezes again (set up 2026-10-30)

Don't reboot. Either route works while the screen is frozen:

| From | Do this |
|---|---|
| The laptop | **Ctrl+Alt+F3**, log in on the text console, run `unfreeze-shell`. It switches the screen back to the desktop by itself (otherwise Ctrl+Alt+F2) |
| The Mac | `ssh -t drn2@<laptop hostname>.local .local/bin/unfreeze-shell` (`hostnamectl --static` on the laptop prints the name) |

`unfreeze-shell` is `CompositorUnfreeze/unfreeze-shell_20261030_192908.sh`, linked from `~/.local/bin`. It:

1. checks that the shell really is hung (a D-Bus property read gets no answer, twice), and does nothing if it answers;
2. saves thread states and the last 15 min of the journal in `~/gnome-shell-hangs/<time>/`;
3. saves a core dump with `gcore` if you type your sudo password (Ctrl+C skips it). The core holds the shell's
   memory, so it stays on this machine;
4. restarts the shell with **SIGINT** instead of SIGKILL, so the "Oh no" screen should not come up (3E). Windows
   stay open;
5. waits for the new shell to answer, and hides the "Oh no" screen if it came up anyway.

`unfreeze-shell --check` only reports; `--help` lists the other options. What is tested and what is not: 3D.

## Summary

- **What hung** (the rescuer saw this live): gnome-shell's main thread blocked on a futex, while a gnome-shell
  thread named `dconf worker` spun at 100% CPU.
- **What set it off [log]:** our own workspace-wallpaper daemon. On every workspace switch it writes a new
  wallpaper to dconf. Both freezes since the Sep 24 fix came after a burst of switches, and in each case the
  last thing the daemon logged before the hang was one of these writes: **Oct 11 13:03:26** and
  **Oct 30 17:04:10**. The daemon was stopped at 19:26 and no longer starts at login (3A).
- **Likely mechanism [source + inference]:** a lock-order deadlock between GJS (the shell's JavaScript engine)
  and GLib's GSettings code. Each wallpaper write hands the shell both halves of it. Every step of the cycle
  exists in the installed code, but it has not yet been caught in a backtrace (section 2).
- **Fix (done 19:26):** stop changing the wallpaper through dconf on every switch (3A). Doing that is also the
  test: if the shell still freezes with the daemon off, section 2 is wrong.
- **Backup:** if it freezes anyway, `unfreeze-shell` recovers it from a text console or over SSH (top of this file).
- **Updates:** the pending GLib and gnome-shell updates fix different hangs. GJS master still has the same
  code, so an upgrade would not fix this either (section 3F).

## 2. Likely mechanism [source; not yet confirmed by a backtrace]

Two threads take the same two locks in opposite order:

```
gnome-shell MAIN THREAD (GJS garbage collection)      "dconf worker" THREAD (a dconf change arrives)
-----------------------------------------------       ----------------------------------------------
1. holds GJS's toggle-queue lock (a spin lock)        1. holds the GSettings backend mutex
   for the whole GC sweep                                while it walks every GSettings in the process
2. frees a dead Gio.Settings, whose cleanup           2. takes a temporary ref on a JS-owned GSettings
   needs the GSettings backend mutex                     -> GJS toggle notification -> needs the
   ==> BLOCKS in futex (forever)                         toggle-queue lock  ==> SPINS at 100% (forever)
```

This matches what the rescuer saw: the main thread in `futex_do_wait` making no progress, `dconf worker` at
99.9% CPU, and the `dconf-service` daemon idle. Neither thread can ever proceed, so only a signal the shell does
not handle ends it: SIGKILL, or SIGINT (3E). SIGTERM does nothing, because the shell handles it in the stuck main
loop. That is why every reboot of a hung shell ends in `timeout`.

### 2.2 Why workspace switches, bursts and load [inference]

- With the daemon, every switch gives the dconf worker a change to dispatch (worker side). It also creates a
  `Gio.Settings` that a later GC frees under the toggle-queue lock (main side). The switch animation itself
  allocates many JS objects (`js/ui/workspaceAnimation.js:38` builds a background manager per workspace),
  so GCs run around switches.
- In a burst, the next write lands while the previous wallpaper's objects are being collected.
- Both critical sections are normally microseconds long. A thread preempted inside one can stretch it to
  milliseconds, which makes an overlap far more likely. That would explain "only under load", but nobody has
  measured it.
- Without the daemon, the shell gets dconf change notifications only when some setting really changes, and it
  rarely frees GSettings objects. So the window almost never opens.

### 2.3 What would confirm it

A backtrace of the next hang (3D) would show:

- `dconf worker`: `ToggleQueue::lock` / `ObjectInstance::wrapped_gobj_toggle_notify` (libgjs), under
  `g_weak_ref_get` and `g_settings_backend_keys_changed` (libgio), under dconf engine frames.
- Main thread: `g_mutex_lock`, under `g_settings_backend_watch_weak_notify` ← `g_object_unref` /
  `g_object_remove_toggle_ref` ← `ObjectInstance::release_native_object` ←
  `update_heap_wrapper_weak_pointers`, under SpiderMonkey (libmozjs) GC frames.

libgjs exports no `ToggleQueue` symbols, and `g_settings_backend_dispatch_signal` is static. Without debug
symbols those frames print as `??`, so use debuginfod (3D).

### 2.4 Upstream status

- GJS master (checked 2026-10-30) still has the busy-wait `ToggleQueue::lock()`, and still takes that lock for
  the whole sweep (`auto locked_queue = ToggleQueue::get_default();`).
- One web search ("gnome-shell hang "dconf worker" thread 100% CPU main thread futex") found no matching report.
  With a backtrace in hand, this is worth reporting to GJS (and to GNOME Shell: `Background` could share one
  interface `Gio.Settings` instead of making one per wallpaper change).

## 3. Solutions

### 3A. Remove the trigger (done 19:26; reversible; also the test)

Done at 19:26. After checking both command lines, `kill` stopped the daemon (PID 5699, running since the Oct 25
login) and its `xprop -spy` child (PID 5823). The autostart entry now says `X-GNOME-Autostart-enabled=false`;
nothing else in it changed. The original is kept as
`~/.config/autostart/workspace-wallpapers.desktop.bak_20261030_192623`. GNOME starts only `*.desktop` files from
that folder, so the backup is not run. The current wallpaper stays.

To undo, restore the original. It takes effect at the next login; the second line also starts the daemon now:

```bash
cp -p ~/.config/autostart/workspace-wallpapers.desktop.bak_20261030_192623 ~/.config/autostart/workspace-wallpapers.desktop && \
  setsid ~/Documents/desktops/workspace-wallpapers-fast.sh --fast-poll >/dev/null 2>&1 &
```

Running this repo's `install.sh` again also puts the autostart entry back, enabled. The entry runs the deployed
copy in `~/Documents/desktops`, not `daemon/` in this repo; the two differ only in `IMAGE_DIR`.

If the shell still freezes with the daemon off, section 2 is wrong. `unfreeze-shell` keeps the evidence (3D).

### 3B. Keep per-workspace wallpapers with less risk (not a fix)

Raise `DEBOUNCE=0.3` to `DEBOUNCE=2` in the daemon (both copies). A burst then produces one write once things
settle, and the write lands after the switch's GC activity. About 6 in 10 of the writes since Sep 24 (4,235 of
6,705) came less than 2 s after the previous switch and would have been merged. Every write that remains still
carries the same risk.

### 3C. Proper fix (needs work; not started)

Do per-workspace wallpapers inside the shell without writing settings: for example, a small GNOME Shell
extension that loads the six images once and swaps the image shown on `active-workspace-changed`. That means no
dconf writes, no change dispatch on the `dconf worker`, and no new `Gio.Settings` per switch. It needs design
and testing, and an extension bug can crash the shell too (recoverable on X11). Then report the deadlock
upstream (2.4).

### 3E. Restart without the "Oh no" screen: SIGINT, not SIGKILL [tested on dummy units, not on the shell]

When the shell dies from SIGKILL, systemd logs `Failed with result 'signal'`, and the unit's
`OnFailure=gnome-session-failed.target` puts up the "Oh no" lockdown. Stopping that screen shuts the session down
(rescuer's notes). Two facts make SIGINT a clean restart instead:

- systemd.service(5), under `SuccessExitStatus=`: besides exit status 0, "except for Type=oneshot, the signals
  SIGHUP, SIGINT, SIGTERM, and SIGPIPE" count as a successful exit. The shell's unit is `Type=notify`.
- gnome-shell does not handle SIGINT or SIGHUP. At 19:21 `/proc/<pid>/status` of the running shell listed as
  caught SIGILL, SIGTRAP, SIGABRT, SIGBUS, SIGFPE, SIGSEGV, SIGTERM and signal 33, and as ignored SIGPIPE and
  SIGXFSZ. So a SIGINT ends the process in the kernel, like SIGKILL, however stuck its threads are.

Test (19:26, systemd 255.4): throwaway `sleep` units with the shell unit's `Restart=always`, `RestartSec=0` and
`SuccessExitStatus=1`, plus an `OnFailure=` pointing to a unit that does not exist:

| Signal | Restarted | systemd's journal for the unit |
|---|---|---|
| SIGINT | yes, new PID | only "Scheduled restart job" |
| SIGHUP | yes, new PID | only "Scheduled restart job" |
| SIGKILL | yes, new PID | "Failed with result 'signal'", "Triggering OnFailure= dependencies" |

The SIGKILL row is what happened to the real shell at 17:25:30, so `unfreeze-shell` uses SIGINT. The
`SuccessExitStatus=SIGKILL` drop-in proposed here at 18:10 is not needed, and was not applied.
